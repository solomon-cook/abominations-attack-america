# Backend and contract audit ledger

This is a source-level audit of the API boundary, room stores, persistence behavior, and operational controls. Automated unit/HTTP checks do not establish production database concurrency, multi-instance socket delivery, or deployment security. The lifecycle fixes below have focused API coverage and independent source review; the Prisma tests use a contract test double rather than live Postgres.

## Audit limits

- The Prisma adapter tests use a contract test double. No live Postgres race, migration application/drift, backup restore, or multi-instance socket test has been recorded for this audit.
- `scripts/verify-account-api-pglite.mjs` applies all nine checked-in migration SQL files directly to in-memory PGlite, then uses the actual API process and Prisma PostgreSQL adapter for sequential account recovery, cookie, claim, match-list, and resume flows. The run is retained at [`output/api-review/account-api-pglite-2026-09-28.json`](../output/api-review/account-api-pglite-2026-09-28.json). It does not exercise Prisma Migrate bookkeeping, durable storage, PostgreSQL MVCC/row locks, or concurrent rollback/race semantics; Prisma Migrate could not be run against the PGlite socket server in this environment.
- The contract test adapter executes `$transaction` callbacks directly and does not roll back prior adapter writes after a later callback error. Expiry regressions use adapter hooks to make the room status/activity snapshot stale immediately before its compare-and-set; they prove guarded code stops before dependent mutations when that CAS affects zero rows. They do not execute a true competing expiry transaction and do not establish rollback atomicity.
- Setup activation and expiry tests use that same adapter double; they demonstrate compare-and-set sequencing and version/event contracts but do not simulate PostgreSQL MVCC, row locks, or serializable relation-filter behavior. Run two-connection Postgres races for activation, account linking, and expiry before treating transaction concurrency proof as complete.
- Idle-expiry policy is not fully identical between stores: Prisma preserves its established exemption for an `ACTIVE` room with at least one account-linked `PLAYER`; the in-memory store expires idle non-completed rooms uniformly. `ABANDONED` rooms are not covered by Prisma's linked-seat exemption. This is an implementation difference, not evidence of physical-rule parity.
- A post-view expiry check closes the stale-read window observed during projection assembly, but the check and returned response are not one atomic database snapshot. A room can still change immediately after that final check; no distributed single-response freshness guarantee is claimed.
- HTTP reads validate the session at authorization time and may finish after its deadline if the view load crosses that boundary. Socket projections recheck the session after loading because long-lived connections have a separate private-delivery boundary.
- The local rate limits are process-local and require a shared limiter or edge policy when scaled across API instances.
- The dependency audit baseline compares known findings to detect drift. A passing baseline check does not remediate or waive the listed advisories.
- Physical-edition rules, board identity, and source-dependent game behavior are covered by the separate [source and rule audit records](unresolved-rules-inventory.md); this backend audit does not approve those rules.
