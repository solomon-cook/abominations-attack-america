# Match replay plan

## User need

The roadmap asks for match replay navigation, bookmarks, export, and shareable spectator replays. These should let a player revisit important decisions and let an invited audience watch a completed public match without rejoining its live room.

## Current data boundary

The engine has deterministic commands and per-command outcome events, but the ordinary room event payload is not a replay source: it does not preserve the accepted command, and setup event payloads retain only the setup phase and action type. New rooms now capture an immutable initial state and accepted setup/game commands in private replay fields, separate from ordinary event payloads. Existing completed rooms predate that capture and cannot be reconstructed reliably from their current snapshots and event records. Ordinary in-memory and Prisma room views still return at most 256 events; the replay API must read the dedicated replay source and apply its own work and response limits.

The event payload also contains fields that can identify drawn or selected cards. A replay endpoint must not return stored internal event payloads as-is. It must construct each replay frame through a spectator-safe projection and omit credentials, private random state, deck order, and private card choices. Private-room matches must not receive shareable public replay URLs.

## Privacy and controls

- Only completed public matches can be opened through a shareable spectator replay. A room code alone must not disclose a private match.
- Exported replays contain no room session tokens, participant IDs, email addresses, private card hands, deck order, or server-only random key.
- Bookmarks stay in the viewer's browser unless a later, separately approved synced-bookmark feature is designed.
- The live room API and its command permissions remain unchanged by read-only replay access.

## Compatibility and replay format

Capture an immutable initial game state and accepted setup/game commands with their authoritative event version, actor seat, control source, and result version. Add an explicit replay schema version and pin board ID/version/content hash and ruleset version. Reconstruct frames with the matching engine/content version, then project each frame for spectators. If a legacy match lacks a complete command history or a supported rules/content version, label it non-replayable rather than approximating it from the final snapshot.

## Cost and limits

Replay data adds database storage per accepted command; navigation and export add API CPU and response egress. Bookmarks add no service storage. Completed public matches use a process-local LRU cache of validated spectator frames to avoid reconstructing the full history for every page. It stores at most 8 MB of serialized frames per match and 16 MB total; cache misses rebuild and parity-check from the persisted source. This reduces repeated work on a single API process but does not provide a shared cache across instances.

A reproducible local in-memory API benchmark in `apps/api/src/server.integration.test.ts` (`REPLAY_BENCHMARK=1 node --import tsx --test src/server.integration.test.ts`) completed the real three-player audited-board route at terminal version 151: the first replay request, which reconstructs and caches the complete 152-frame history, returned its terminal page in 213 ms; the full spectator-projected JSON export was 2,445,218 bytes and took 26 ms from cache; complete 13-page navigation returned 2,640,408 cumulative bytes in 71 ms from cache. The page walk checked the full 0–151 version range without gaps or forward-frame duplicates, and every page stayed under 700 KB. The export stays under its 8 MB limit and reconstruction under 2,048 versions. These are one-run local in-memory measurements, not a hosted latency or capacity guarantee; frame serialization also makes replay egress larger than the stored command source.

The repeatable real-PostgreSQL local probe is `POSTGRES_BIN_DIR=... npm run replay:postgres:local:benchmark`. It creates a temporary PostgreSQL 17 cluster, applies the current Prisma migrations, drives a completed three-player audited-board API match through America Saved using Prisma, measures replay reconstruction/export/full paging over HTTP, reads persisted row and relation sizes, and removes the temporary cluster. The 11 October 2026 run produced terminal version 189 with 189/189 replay source rows: 22,868 bytes of replay-command JSON (about 121 bytes per accepted version), 87,260 bytes of event-payload JSON, and 245,760 bytes for the `GameEvent` relation including indexes. The whole test database grew 2,965,504 bytes from its post-migration baseline for the match and associated room data. First full reconstruction took 332 ms and returned a 26,139-byte terminal page; cached JSON export was 3,410,127 bytes in 45 ms; 16 pages returned 3,683,612 cumulative bytes in 138 ms. All 189 versions replayed to the exact final state. The benchmark also fixed a Postgres parity defect: JSONB can reorder object keys, so state equality now canonicalizes object keys while preserving array order. This is one local sample on one API process, not selected-host latency, managed capacity, or realistic public egress. The larger full-history page walk includes repeated cursor-base frames by design.

The hosted PostgreSQL row/storage size, query/egress under realistic load, and cleanup/retention policy remain open. Prisma keeps replay commands on `GameEvent` rows for as long as their room exists; the ordinary in-memory event view retains only the newest 256 events, while replay reconstruction permits up to 2,048 versions. The user-selected managed PostgreSQL host is not provisioned, so the local sample cannot close the selected-host measurement requirement. A candidate retention policy for owner review is to retain completed public replay sources for 90 days, keep stale incomplete-room retention separate, and preserve only the existing anonymized match-stat history after replay-source expiry. No cleanup job or expiry behavior should be enabled until the owner approves the effect on share links and account history. Vendor-specific storage/egress cost remains tied to the open hosting decision in `docs/hosting-decision-record.md`.

## Delivery stages

1. [x] Record the immutable initial state and accepted setup/game command stream in both stores, without exposing either in ordinary room views. Memory and Prisma adapter tests verify the stored inputs and public room-view boundary. A temporary local PostgreSQL 17 run applies all current migrations and verifies persisted replay sources; migration and deployed restart evidence against the selected managed PostgreSQL service remain open.
2. [x] Add `GET /rooms/{code}/replay?fromVersion=&limit=` for completed public matches. It rebuilds each frame from the private initial state and versioned setup, start, and command records; requires complete version coverage and a reconstructed terminal state that matches the stored state; emits spectator projections with board/ruleset identity; and returns an explicit non-replayable reason for private, live, legacy, incomplete, oversized, or unsupported histories. Pages cap at 12 frames and 700 KB; reconstruction caps at 2,048 versions. Store, route integration, privacy, paging, legacy tests, and the temporary-PostgreSQL replay route benchmark pass.
3. [x] Add previous/next navigation, an event/version index, local bookmarks, and read-only board rendering. `/?replay=ROOMCODE` opens the player-facing view; the viewer requests additional bounded pages as needed and keeps bookmarks in browser-local storage. `npm run match-replay:browser:verify` covers keyboard and mobile navigation, board display, backward/forward navigation across a page boundary, bookmark persistence after reload, and absence of live command requests.
4. [x] Add secret-free JSON export and a share link that opens the same public spectator replay. `GET /rooms/{code}/replay/export` returns versioned spectator-projected frames for completed public matches only and refuses exports over 8 MB.    - [x] Measure persisted replay-source size and query/egress on a temporary local PostgreSQL 17 candidate run (`npm run replay:postgres:local:benchmark`); a three-player version-189 match stored 189 replay commands (22,868 bytes of command JSON; 245,760 bytes for the `GameEvent` relation including indexes) and successfully reconstructed, exported, and paged. ## Acceptance boundary

The roadmap replay feature stays open until all five stages and their tests/player acceptance pass. A timeline of event text alone is not a complete board replay.
