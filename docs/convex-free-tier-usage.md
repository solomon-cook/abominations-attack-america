# Convex usage and realtime budget

Local singleplayer is an in-browser game. A source audit of the app startup path found no Convex request on an ordinary app open or solo match: saved online rooms are not restored automatically, the account panel makes no request while closed, and the public-room list is fetched only when a player asks to refresh it. A saved online room can be resumed from the multiplayer menu. An explicit TV viewing link still connects to its room on open; account, multiplayer, and replay links also intentionally use their requested online features. This keeps ordinary singleplayer play off Convex.

The checked-in production baseline (`499e296`) explains the reported singleplayer traffic: it restored a saved room during app startup, and its collapsed account panel queried the current account and leaderboard when mounted. A signed-in player could then trigger four more separate account requests. The current working tree removes the automatic room read, defers account requests until the panel is opened, loads account details in one request, and fetches the leaderboard only when its section is opened. These fixes are local and have not reached production yet.

## Leaving Convex without losing existing data

The candidate Prisma/WebSocket route can receive multiplayer traffic without Convex, while retaining the same event-driven updates for connected players. A one-time importer now reads an already-downloaded, extracted Convex backup and writes its durable rooms, replay events, accounts, sessions, friends, and match statistics to an empty Prisma database in batches inside one transaction. Its `--check` mode validates the backup structure and references without connecting to a database. It expands compressed room snapshots and restores the starting replay state. It intentionally drops short-lived presence, runtime scheduling, and WebSocket tickets; room participants reconnect after the move. The importer refuses to run against a non-empty target. Username-only accounts are retained by allowing a missing account email in Prisma.

The importer has not been run against real data. Creating/downloading a Convex backup itself reads the deployment's data and can add database I/O, so neither a production backup nor an import was run as part of this local work. Before cutover, take a backup at a deliberate time, import it into the intended Prisma target, compare row counts and integrity, then verify the preview route with representative multiplayer sessions. Production currently still routes through Convex; this branch has not been deployed.

On the Prisma WebSocket path, a normal accepted move writes the room snapshot and one replay event in a transaction. The action's retry key is stored on that event, removing the separate command-receipt write. After the commit, the one shared room projection read for connected players also supplies the sender's acknowledgment. Calls that need presence, accounts, public-room search, or replay still touch Prisma only when those features are used; ordinary local singleplayer remains in-browser.

The Prisma server no longer runs its five-second global bot-takeover scan. Bot turns are processed after relevant room actions, and a disconnected seat gets one delayed room-scoped takeover check; later room activity also catches an overdue takeover if the serverless process restarted before that timer fired. The in-memory development store keeps its local bot worker, which does not query a database.

WebSocket connect now relies on the shared room broadcast for its initial view instead of sending a per-socket view and immediately broadcasting it again. Disconnect handling returns only whether the current connection actually changed the seat, so stale socket closes do not trigger extra room reads or broadcasts. Room-status refresh reads player seats and room state together, and skips status writes when the status is already correct.

The HTTP fallback now runs bot/takeover processing only when the returned room contains a bot-controlled or disconnected player. Adding a bot in the waiting lobby no longer starts a bot scan before the match begins. Human-only rooms therefore avoid the follow-up scans while preserving automated setup, takeover, and bot-turn processing where needed.

Each authenticated Prisma room request now loads the room and its matching participant token in one joined read instead of reading the room and then querying the participant separately. The extra linked-account check for idle-room expiry runs only after the room has actually passed its idle timeout; active room traffic avoids that count query.

The WebSocket fan-out projection no longer reads up to 256 persisted event rows on every room update. The browser does not consume `RoomView.events`; it receives current state and its in-state game log, while replay history is loaded through the replay feature. This removes a high-churn read from each realtime broadcast without delaying or polling for opponents' decisions.

## Production baseline

On 2026-11-18, Convex's CLI reported 11,198 function calls and 3.044 GB of database I/O month-to-date for production deployment `careful-ibis-752`; it reported no usage limits configured. Convex's published Free allowance is 1 million function calls and 1 GB of database I/O per month. Function-call volume is well below that allowance, while this deployment's database I/O is already over it. This deployment-only reading does not include any usage from other deployments on the team. See [Convex limits](https://docs.convex.dev/production/state/limits).

The retained production function-log history returned 141 completions from 2026-11-17 09:45–11:19 UTC. In that slice, the old HTTP rate-limit mutation ran 44 times and wrote about 18 KB total; leaderboard queries ran 19 times and read about 7.5 KB total. No room functions appeared in that slice, so it does not explain the 3.044 GB month-to-date I/O and is not evidence of a representative multiplayer session. Per-feature attribution for most of the month's I/O remains unavailable from the retained logs.

Multiplayer keeps Convex's live room query subscription. The client receives game-state changes over Convex's realtime connection. High-churn game state and low-churn participant metadata now use separate subscriptions, so every accepted move does not reread and resend the participant list. The live state query and room mutation responses also avoid replay-event reads. Replay rows store the command needed to reconstruct a move and a compact retry receipt; they do not duplicate the full presentation details already in the live snapshot. Room game state is gzip-compressed into Convex bytes for storage and expanded before it reaches the client; old object-shaped state is still readable and migrates on its next write. A local measurement of a four-player opening state shrank from 10.7 KB to 2.3 KB (about 78% smaller). New rooms keep the immutable replay starting state in a separate seed table, outside the room row read and rewritten on every move; legacy starting states move there on the room's next game-state write. The room snapshot retains only the latest 24 event details and 24 text-log lines for immediate UI feedback; full history remains in separate replay records and is loaded only for replay features. Trophy attribution is compacted into a small durable list as old live events are trimmed. After a prolonged disconnect or a burst of more than 24 actions between client updates, some animations may be skipped while the authoritative room snapshot restores the current game state.

Participant reads on room views and gameplay paths are bounded to the four player seats, plus the requesting spectator when needed. Large spectator groups therefore do not make every player action, bot step, readiness change, or participant subscription read all spectator rows. The public-room browser reads at most 21 spectator rows per listed room and displays `20+` above that threshold; it only runs when that feature is opened.

The existing Prisma WebSocket server builds all connected viewers' private room projections from one room read per update, and that fan-out omits replay rows the browser does not consume. A build selects this transport when Convex is absent and `VITE_ENABLE_WEBSOCKETS=true`; `VITE_API_URL` may point to the Prisma API, and otherwise a production build uses the same-origin `/api/game` route. While the socket is open, its ping/pong and close handling replace the browser's database heartbeat and duplicate disconnect request. On socket loss, the browser retries with exponential backoff and uses polling only while it reconnects. The candidate now routes `/api/game/*` through the Prisma Node server, including WebSocket upgrades; its Postgres notification listener fans room changes across function instances. The live production build still has a Convex client and uses the separate `/api/*` Convex proxy. Clearing the Convex client URL on its own is not a production cutover: the Prisma database must contain verified room and account data first, then the preview transport and production route need runtime verification. Vercel closes WebSockets at the function duration limit, so reconnect remains part of the transport. See [Vercel WebSocket GA](https://vercel.com/changelog/websocket-support-is-now-generally-available) and [Vercel WebSocket connection behavior](https://vercel.com/kb/guide/do-vercel-serverless-functions-support-websocket-connections).

To reduce background presence traffic, clients in unfinished rooms send a heartbeat every five minutes; heartbeats and disconnect writes stop once the match is completed. The backend considers a participant stale after six minutes. A heartbeat authenticates by session token and connection ID, then touches only the separate presence record; it does not reread or decompress the room snapshot. Heartbeat timestamps and presence-scheduler bookkeeping live outside room-visible records, so neither heartbeats nor routine scheduled checks by themselves wake every player's room subscription. After its initial check, the shared presence job schedules itself for the next stale-presence, bot-takeover, or room-expiry deadline instead of polling every three minutes. An abrupt disconnect is detected within six minutes of its last heartbeat, then bot takeover is applied if another player is still present; actual game decisions still update through realtime subscriptions as soon as the server accepts them. Normal room actions no longer read scheduler state just to keep the check alive. Opted-in friend presence now uses a six-minute expiry and a five-minute visible-panel refresh, down from four-minute refreshes; this path is separate from room gameplay.

Room commands and room reads use the Convex client directly instead of wrapping a Convex function call inside a second HTTP action. Normal game moves no longer query or write a separate command-receipt row; stale retries check the replay event already stored for that room version. Gameplay and setup acknowledgements contain only game state, version, and status; the live subscription supplies participant and room metadata. Reconnecting to an active room no longer returns a second full room snapshot or writes the room document just to refresh metadata; the state and participant subscriptions deliver the current view. Rooms record whether they contain bots, so ordinary game and setup moves do not scan participant rows just to decide whether to schedule a bot. Legacy rooms without this flag are checked once on their next accepted move. Starting a match with empty seats fills all missing bot seats in one mutation instead of one mutation and participant-list read per bot. Room privacy and bot handoff use direct mutations too, and bot handoff no longer sends a redundant disconnect mutation. Opening a signed-in account panel now loads account, recent games, stats, social, and privacy data through one authenticated dashboard request instead of five separate authenticated requests. The dashboard only loads the most recent 20 account-linked games. An account builds its lifetime-stats summary the first time its dashboard or public profile is viewed. Totals stay on the account row and later matches update that already-read account, avoiding repeat history scans and a separate summary-table lookup. Accounts that never use stats/profile views do not receive the extra match-end summary write. Opted-in friend presence refreshes every five minutes only while the account panel is open; its online status expires after six minutes without a refresh. Account and authentication endpoints remain behind the HTTP proxy. The general HTTP rate limiter now runs in the Vercel proxy's process memory instead of writing a counter to Convex for every request. That limiter is best-effort per running Vercel instance; direct calls to the public Convex HTTP endpoint bypass it.

Expected Convex usage remains for multiplayer room creation/join, game actions, subscription recomputations as room data changes, periodic presence heartbeats, account features a player opens, and scheduled room cleanup/bot work. This design targets ordinary singleplayer at zero Convex calls and keeps multiplayer traffic event-driven, but it does not guarantee the Free plan for every possible user count or play duration. Check the Convex usage page after deploying and playing a representative multiplayer session before relying on the warning threshold.

For an ordinary accepted multiplayer move, the backend still writes the updated room state and one replay event. Each connected player has an authenticated live state query that reacts to the room update. Participant rows are now on a separate query and are not reread for every move. This keeps decisions realtime and durable, but the state document size and number of connected players still affect database I/O; reducing unnecessary queries cannot make the 1 GB monthly allowance a guarantee.
