# Staged site and game overhaul plan

## Objective

Improve the full Abominations Attack America experience—game rules and bots, web UI, API and persistence, documentation, and runtime performance—through independently reviewable slices. Keep the current visual quality and persisted-match compatibility. Treat the user's physical edition as the final authority for rules and board facts. Do not guess at source-dependent behavior.

This is an implementation plan and a status ledger. Passing code checks establish implementation behavior only; they do not establish physical-rule parity or release approval.

## Coordination

- Keep the work on the isolated `codex/staged-game-overhaul` branch until the integrated slices and their evidence have been reviewed.
- The integration lead owns this plan, shared contracts, conflict resolution, gate execution, and the final evidence index. Each workstream has one implementation owner and a separate read-only reviewer; agents work on disjoint paths or submit findings before another owner edits the same path.
- Workstreams may run in parallel after their dependencies are met. The integration lead integrates in dependency order, records the owner/reviewer decision and evidence, then runs cross-stream checks. A reviewer reports findings to the lead; the lead assigns any fix to the original owner or a newly designated owner.
- Prefer small changes with a clear acceptance check. Preserve the existing board IDs, content hashes, save migrations, and full-quality artwork unless a compatibility or measured-performance case is documented first.
- Record a finding as a defect only when its behavior is reproduced or its source contract is explicit. Mark physical-edition questions as blocked with the exact evidence needed.
- Treat this plan, the [developer guide](development.md), [frontend surface audit ledger](ui-surface-audit.md), [backend audit ledger](backend-audit.md), [bot strategy audit](bot-strategy-audit.md), [performance baseline](performance-baseline.md), [rule/source records](rules-source.md), [unresolved source inventory](unresolved-rules-inventory.md), and [release proof report](release-proof-report.md) as the coordination record. Update status and evidence in the owning document when each slice changes.

## Work sequence

### 1. Establish trustworthy status and working boundaries

**Purpose:** make it possible to tell prototype behavior, transcribed evidence, physical-source verification, and release approval apart.

- Keep the user-facing board description explicit that the active 336-cell board is a playtest candidate while independent source review and production sign-off remain open.
- Reconcile any contradictory source, board-audit, approval, or runtime wording. Preserve persisted board identifiers and hashes during this documentation pass.
- Keep a concise code map, local startup steps, and validation-command guide in `docs/development.md`; add focused API contract documentation where endpoint behavior is not discoverable from the code map.
- Complete a code-quality and maintainability review across the engine, API, web client, and shared contracts. Record concrete findings by file and impact, distinguish verified defects from cleanup opportunities, and avoid broad rewrites without behavioral evidence.
- Audit documentation coverage against the actual route, component, state, storage, and deployment surfaces. Check command accuracy, source attribution, generated-document provenance, and whether public APIs and lifecycle semantics are described consistently by both memory and database-backed stores.
- Keep unresolved board, card, component, setup, and exception facts visible. A type named `verified`, validator pass, or old approval phrase cannot substitute for physical-source evidence.

**Acceptance:** source/status docs agree on what was transcribed, what was compared with the physical edition, and what remains release-blocked; local links and documented commands are accurate. The code/documentation audit has a coverage checklist, prioritized findings, and a clear record of which findings were fixed, deferred, or source-blocked.

### 2. Fix verified game and service defects

**Purpose:** correct behaviors with direct code or test evidence without broadening rules based on assumptions.

- Stop bot defensive path scoring from treating its own monster as a rival threat; keep positive scoring for living rival routes.
- Exercise 3-seat and 4-seat bot matches deterministically. Record completed turns, accepted/invalid actions, and the intentionally short sample duration.
- Keep room projections private across socket replacement, session rotation, account claim/resume, reconnect, and concurrent handshakes. Validate the live connection lease before sending projections.
- Align explicit disconnect/reconnect requests with the active server-side socket lease and broadcast actual presence transitions.
- Preserve event-revision, command idempotency, player/spectator projection, and persisted-snapshot contracts.
- Audit the full backend boundary: account and session authorization, guest/player/spectator permissions, endpoint request/response/error contracts, memory-versus-Prisma behavior, saved-match and migration compatibility, concurrency, operational logging/health, and security-sensitive data exposure. Track unresolved store lifecycle differences instead of documenting them as guarantees.

**Acceptance:** engine and API regression suites pass; API typecheck passes; stale sessions cannot receive later private room updates; bot samples finish one turn for every configured seat without invalid actions. Backend findings include a reproduction or source contract, affected endpoint/store, severity, and regression evidence or a stated follow-up.

### 3. Audit and refine the interface

**Purpose:** make every gameplay surface understandable, reachable, and usable at desktop, tablet, and phone sizes.

- Audit the game shell, setup, map controls, status HUD, record, command dock, move queue, deployment/research sheet, cards, challenge surfaces, and all submenus, drawers, popovers, and dialogs.
- Maintain the [surface inventory/findings ledger](ui-surface-audit.md) for every menu, submenu, drawer, popover, and dialog, with its entry point, key states, viewport/keyboard coverage, and review result. Include non-game flows: landing, local setup, online create/join, lobby, account/recovery, profiles/leaderboards, spectator entry/playback, reconnect, and terminal/post-game states. Reconcile this ledger with the existing [landing-to-game UX plan](landing-to-game-ux-plan.md) and [UI redesign plan](ui-ux-redesign-plan.md) rather than treating the tray checks as full-surface coverage.
- During active gameplay, keep a compact always-visible shortcut to the active player's main-branch military sheet with deployed/reserve counts; the starting-deployment setup keeps its dedicated troop-placement sheet. Preserve the existing full sheet and board artwork.
- Ensure the shortcut clears the movement-order checklist, command dock, and record controls at responsive widths. Keep it keyboard accessible and update its counts after unit transitions.
- Allow Escape to dismiss the nonmodal military drawer while focus is on the drawer or the interactive board, and restore focus to the opener.
- Use browser and keyboard acceptance evidence in addition to source-only accessibility/responsive contracts. Keep unresolved manual assistive-technology checks explicit.

**Acceptance:** browser checks cover 1280×720, 900×700, 768×600, 834×1112, 390×844, and 320×740; the tray is visible and unobstructed with the mobile command/record sheet collapsed and expanded, including when Map is selected; counts are named accessibly, Enter/tap opens the sheet, Escape closes it from outside the drawer, and normal game controls remain operable. The surface ledger accounts for every listed flow and each menu/drawer/dialog has evidence or an explicitly open manual check; tray-specific evidence alone does not close the UI audit.

### 4. Measure and optimize runtime performance

**Purpose:** improve loading and interaction speed without reducing the visual quality of the board, monsters, cards, or interface.

- Record production bundle and gzip sizes, initial-load and first-selection measurements, and the exact screen/state, browser, and throttling profile used for each baseline; add steady-state rendering and pan/zoom profiles before rendering claims.
- Profile board interaction and rendering before changing component boundaries or algorithms. Trace large dependency contributions before choosing code splitting.
- Prefer dead-code removal, lazy loading of noninitial experiences, and avoiding redundant work over reducing artwork resolution, removing detail, or changing visual assets.
- Compare the same build and browser scenarios after each optimization; keep only improvements that exceed measurement noise and do not regress rendering or accessibility.
- Classify the current BoardReview lazy chunk as a route-isolation/payload change only: measured entry bytes fell slightly, but no user-visible speed gain is established. Do not cite it as a performance win unless repeatable loading or interaction profiles confirm one.
- A matched seven-run comparison of the movement-adjacency change is complete, with alternating run order, production builds, and same-route desktop/phone visual checks. Timing ranges overlap in every case, so it does not establish a reliable user-visible speedup. Keep the optimization for its engine-side work reduction only; do not claim browser speed improvement. See [`performance-baseline.md`](performance-baseline.md#matched-adjacency-cache-browser-comparison).
- The next graphics-preserving camera candidate is to prioritize resolution upgrades for terrain cells inside the viewport over tiles in the 300 px prefetch margin. Existing traces suggest that visible 1024 px requests run at Low priority, but this is a single instrumented capture, not a baseline. The seven-pair measurement, decode/source checks, pan-follow-in test, first-selection guardrail, and screenshot acceptance are specified in [`performance-baseline.md`](performance-baseline.md#next-candidate-visible-terrain-upgrade-prioritization); no art or final-resolution policy change is proposed.
- Add explicit budgets after a stable baseline is agreed. Do not hide a bundle warning by only raising the threshold.

**Acceptance:** each retained optimization has repeated before/after data under the same representative conditions, a repeatable command/scenario, and visual-regression evidence showing the existing graphics remain intact. Cold-load, first-selection, and warmed pan/zoom traces now exist. The nearby-only subscription trial shows a structural reduction in potential offscreen state notifications, but noisy camera timing and incomplete post-zoom image decoding do not establish a user-visible speed improvement; React render attribution and a fully decoded visual comparison remain open.

### 5. Close physical-edition parity questions

**Purpose:** verify the digital rules against the edition the user owns, without treating a player aid, catalogue, or prior transcription as the final authority.

- Capture and review every source category in the [unresolved rule-bearing inventory](unresolved-rules-inventory.md): board geometry/features/coordinates/co-locations/lake barriers; monster and unit statistics/abilities; setup and branch deployment; Navy Nuclear Submarine lifecycle; Mutation and Research card effects; National Guard control; giant-unit placement; and component-dependent special cases.
- Compare each physical fact with its typed definition and record image/page evidence plus any ambiguity. Label an intentional digital adaptation as a ruling, not as printed text.
- Implement only after the applicable physical fact and interpretation are recorded; add focused engine, API-projection, and interface acceptance for each confirmed change.
- Keep board promotion and release sign-off pending until all required board and rule evidence is reviewed.

**Acceptance:** every resolved item links to physical-edition evidence, an implementation location, a focused behavior check, and the required human sign-off. Items without evidence remain blocked and are not filled with guessed values.

### 6. Integrate and prepare a reviewable release candidate

**Purpose:** verify interactions between the workstreams before proposing any release action.

- Run the focused checks for each changed slice, then the repository verification gate when all parallel work is integrated.
- Recheck supported browsers, keyboard flow, persistence migration compatibility, API privacy, documentation links, dependency/build status, and the release-blocker report.
- Preserve the graphical baseline and attach concise evidence to the owning documents. Do not claim source parity while physical review is pending.
- Treat these as non-waivable release blockers: unresolved physical-source/rule sign-off, unresolved production dependency advisories, required manual accessibility review, production persistence/deployment health, and production-browser smoke evidence. Do not deploy, merge, or promote the board while any blocker remains.

**Acceptance:** all required automated checks pass; known nonautomated checks and source gates are listed with owners and evidence needed; the user receives a reviewable summary before any deployment or merge.
