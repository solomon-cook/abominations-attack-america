# Code maintainability audit

This is a prioritized source-level findings ledger for the staged overhaul. It records type-safety and module-boundary risks separately from reproduced runtime defects. The entries below are review findings, not proof that the listed code currently fails at runtime. Changes should stay incremental, preserve the persisted-game and wire contracts, and add focused behavior evidence before a finding is closed.

### Compatibility-sensitive seams

- `MATCH_STATE_SCHEMA_VERSION = 2` (21), `COMMAND_PROTOCOL_VERSION = 1` (554), `migrateGameState` (628), and the board registry/hash check in `boardForState` (748) define saved-room and command boundaries. Migration recomputes pending decisions and converts legacy v1 locations to v2; unsupported versions fail closed.
- `pendingDecision` is serialized in `GameState` and recomputed by migration, while phase resolvers and command branches assign it directly; `pendingDecisionForState` is at line 679. Any shape change needs API/UI projection and saved-state compatibility coverage.
- `resolveFightResult` and `resolvePendingMultiTargetFight` maintain combat continuation; `useResearchCard` and `useMutationInBattle` also inspect Challenge state. A change to one effect may touch several phase paths.
- Direct helpers and wrappers (`moveMonster`, `moveUnit`, `resolveFight`, `resolveEncounter`, deployment helpers) are exported beside `applyCommand` and the protocol-aware envelope. The API uses the envelope, but UI, development tooling, and tests also import direct helpers; narrowing exports requires a caller/compatibility inventory.
- `index.ts` re-exports board, cards, setup, bots, effects, units, and monsters while also defining development fixtures. Callers can therefore depend on convenient development data through the broad package entry point.

These are code-navigation and type-contract risks, not reproduced gameplay defects. A future extraction should start with a dependency map and explicit event/state round-trip checks; source-sensitive rules and migration paths should not move until their owners are clear.

## Audit boundary and close criteria

The review inspected first-party TypeScript for the findings above, the shared room-event contract, and the two largest application modules. It is an initial prioritized review, not a claim that every function or type in the repository has been exhaustively reviewed. Generated Prisma client code is excluded from type-debt findings.

Close a finding only with a scoped diff, focused tests or checks showing behavior/contract preservation, an updated finding disposition, and a note about any compatibility boundary. For module-boundary candidates, require a concrete ownership problem and a testable seam before refactoring. The physical-edition source gate remains independent of code organization and type safety.
